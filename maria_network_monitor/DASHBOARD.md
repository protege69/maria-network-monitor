# Автоматический dashboard Maria Network Monitor

## Что подключается один раз

Приложение само собирает устройства и поддерживает файлы dashboard. Home Assistant нужно один раз подключить к этим файлам. После этого новые static DHCP leases, состояния, принтеры и их доступные метрики появляются в карточках автоматически.

Dashboard использует один локальный JavaScript-модуль, поставляемый вместе с приложением. HACS и сторонние карточки устанавливать не нужно. Пользовательские dashboards остаются на месте.

## Подключение в Home Assistant OS / Supervisor

1. Сделайте резервную копию приложения и конфигурации HA. Обновите приложение до 1.3.0, сохраните существующие credentials и `sites`. `dashboard_enabled` по умолчанию включён; для старых options отсутствие этого ключа также означает `true`.
2. Запустите приложение. В журнале должно появиться `Dashboard files ready`. Генератор создаёт:
   - в каталоге конфигурации HA: `maria_network_monitor/maria-network-monitor.yaml`;
   - в каталоге конфигурации HA: `www/maria_network_monitor/maria-network-card.js`;
   - доступную запасную копию обоих файлов в `/share/maria_network_monitor`;
   - внутреннюю запасную копию в `/data/dashboard`.
3. В настройках dashboards откройте управление Resources (при необходимости включите расширенный режим профиля). Добавьте ресурс типа **JavaScript module**:

   ```text
   /local/maria_network_monitor/maria-network-card.js?v=1.3.0
   ```

   Если ресурс с этим путём уже есть, обновите его URL вместо создания второго. Если ваши resources управляются YAML, дополните существующий список `lovelace.resources`, сохранив его настройки и остальные записи:

   ```yaml
   # Только для уже используемого resource_mode: yaml
   resources:
     - url: /local/maria_network_monitor/maria-network-card.js?v=1.3.0
       type: module
   ```

4. В `configuration.yaml` дополните существующий `lovelace.dashboards` одной записью. Не добавляйте второй ключ `lovelace`, не заменяйте остальные dashboards и не переключайте основной dashboard в YAML mode:

   ```yaml
   lovelace:
     dashboards:
       maria-network-monitor:
         mode: yaml
         title: Maria Network Monitor
         icon: mdi:lan
         show_in_sidebar: true
         filename: maria_network_monitor/maria-network-monitor.yaml
   ```

   Если у вас уже есть `lovelace: !include ...`, внесите `dashboards` в подключаемый файл. Если ключ `maria-network-monitor` уже занят чужим dashboard, выберите другой свободный ключ с дефисом; ссылки на views используют фактический URL текущего dashboard.
5. Проверьте конфигурацию штатным средством HA и перезапустите HA. Откройте **Maria Network Monitor**. Убедитесь, что MQTT integration получает новые inventory и числовые сводки филиалов.

Приложение получает writable mounts каталогов конфигурации HA и `/share`, чтобы поддерживать свои файлы. Оно не изменяет `configuration.yaml`, `.storage` или регистрацию dashboards. Отключение `dashboard_enabled` прекращает генерацию/публикацию dashboard, но намеренно не удаляет уже зарегистрированный dashboard и его retained entities. Сбор существующих устройств продолжает работать.

## Если запись в каталог HA невозможна

Мониторинг продолжит работать; журнал укажет причину отказа экспорта. Через Samba `/share` или подходящий файловый редактор заберите:

- `/share/maria_network_monitor/maria-network-monitor.yaml`;
- `/share/maria_network_monitor/maria-network-card.js`.

Скопируйте YAML в `maria_network_monitor/` каталога конфигурации HA, а JS — в `www/maria_network_monitor/`. Затем выполните шаги 3–5 выше. Если `/share` также недоступен, внутренняя копия остаётся в `/data/dashboard` приложения; её можно извлечь из резервной копии приложения. При отсутствии успешных записей во все каталоги необходимо исправить доступ к одному из них — файл нельзя считать сгенерированным лишь по факту старта процесса.

Устройства внутри существующих views обновляются через MQTT и после ручного копирования YAML. При добавлении/переименовании `sites` потребуется скопировать новый YAML; при рабочем mount это делает приложение на старте самостоятельно. После изменения списка views воспользуйтесь меню dashboard → **Refresh**. Ресурс и dashboard повторно регистрировать не нужно.

## Что видно на странице

- Главная: MikroTik/API, online/offline устройств, проблемные принтеры, свежесть опроса и переход в филиал.
- Филиал: принтеры, рабочие места, камеры, точки доступа, серверы, телефония, неизвестные устройства.
- SIP/SIPS телефоны входят в телефонию / VoIP: распознавание по имени/hostname и доступным TCP 5060/5061. SIP по UDP не проверяется активными запросами; связь по-прежнему определяется ping/TCP/ARP. Это состояние сетевой доступности, а не подтверждение регистрации на АТС.
- Принтер: связь, общий счётчик страниц, состояние/очередь/приём заданий, toner, drum/OPC/waste toner, если источник их сообщает.
- Offline: красная граница и явная подпись. Toner `<=20%`: янтарная полоса и предупреждение. Waste toner: значение источника без правила «низкий процент = плохо».
- При сбое RouterOS: список сохраняется, counts не выдаются за актуальные. При остановке монитора: карточки показывают отсутствие свежих данных.
- Нажатие на устройство/счётчик открывает more-info существующей MQTT entity. Реальный `entity_id` определяется через registry, включая пользовательские переименования. Если sensor ещё не обнаружен, история появится после его discovery. Доступ к registry может быть ограничен ролью пользователя; показ текущего inventory от этого не зависит.

IPP/SNMP кеш может показывать последнее известное значение даже когда принтер офлайн. Даты успешных опросов доступны в карточке. SNMP используется как fallback расходников, если IPP не сообщил ни одного marker; дополнительно dashboard показывает SNMP drum/OPC и waste toner, если их тип отсутствует среди IPP markers. Тонер из двух источников не дублируется. Полнота зависит от реализации протоколов конкретным принтером. Неизвестный процент показывается как отсутствие данных.

## История и отчёты

«Всего страниц» — общий счётчик, **не** количество за сутки. В 1.3.0 ежедневный отчёт ещё не реализован. Подробнее о корректной агрегации, сбросах счётчика и пропусках опроса — в `ARCHITECTURE.md`.

Числовые MQTT sensors филиала и существующие page-counter sensors можно хранить через Recorder. Найдите реальные `entity_id` диагностических **Inventory** sensors и исключите только их из Recorder, чтобы не записывать большие списки устройств каждый цикл:

```yaml
recorder:
  exclude:
    entities:
      - sensor.replace_with_actual_inventory_entity_id
```

Объедините это с существующей конфигурацией Recorder, не заменяя её. Не исключайте online/offline/problem-count sensors и page counters, если нужна их история. В примере показан placeholder, а не предсказанный ID.

## Совместимость и диагностика

- Идентификаторы устройств, topics и cache v1.2.0 сохраняются. Перед откатом восстановите backup, если нужно вернуть options/mounts к предыдущей версии.
- Названия sites должны давать разные legacy router slugs (латинские буквы/цифры после замены разделителей). Например, несколько названий только кириллицей дадут одинаковый legacy slug: запуск остановится с объяснением вместо смешивания роутеров. Одна существующая такая запись сохраняет прежний ID. Идентификаторы новых dashboard views сами по себе Unicode поддерживают.
- MAC считается глобальным ID как в v1.2.0. Один MAC не должен обозначать разные физические устройства в разных филиалах.
- Если видите `Custom element doesn't exist: maria-network-card`, проверьте путь/тип ресурса, загрузку `/local/...`, затем обновите resource cache браузера. Не создавайте второй dashboard.
- Если данные не появляются, проверьте MQTT integration, retained topics `maria-monitor/dashboard/.../state`, журнал приложения и включённый `dashboard_enabled`.
- Если output-файл уже существует без заголовка генератора, приложение откажется его перезаписать. Сохраните его отдельно и освободите только путь, принадлежащий Maria.
